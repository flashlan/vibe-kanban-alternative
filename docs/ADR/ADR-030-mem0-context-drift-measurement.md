# ADR-030: Measure Context Loss/Drift Across mem0 Stage Handoffs

- **Status**: Accepted
- **Date**: 2026-08-21

## Context

ADR-028 made mem0 recall/save agentic: each pipeline stage calls `memory_search` (scoped, ranked, capped to `limit`) before starting and `memory_save` after finishing. That ranking/cap is exactly where two failure modes can happen at a stage handoff, and neither was observable before this change:

- **Loss**: a fact stage N saved for the current task doesn't make it into stage N+1's top-`limit` results, crowded out by unrelated memory already in the repo's shared store.
- **Drift**: unrelated ("noise") memory outranks the actual signal, so the next stage recalls facts that don't belong to the task in front of it.

Before this ADR, `crates/mcp/src/task_server/tools/mem0.rs::memory_search` computed a `score` per hit (used internally to sort/dedupe/cap — `Mem0VectorHit.score`) but discarded it before returning to the caller and before logging; the only signal available was `tracing::info!(hits = memories.len())` — a count, not a relevance measure. There was no test anywhere that exercised recall quality; `mem0-vk/test/test.ts` is a wiring smoke test (does the endpoint respond, does storage/search round-trip work) with a positional character-histogram stub embedding that has no similarity structure — two different strings embed near-arbitrarily relative to each other, so it could never have caught a ranking regression.

Note: `SPEC.md`/`IMPLEMENTATION_PLAN.md` (the raw-text handoff artifact in the Swarm pipeline, see `assets/pipelines/swarm-multi-agent.toml`) is read whole by the next stage — nothing is ranked or capped, so there's no analogous "loss" to measure there; the only handoff channel with a structural mechanism for dropping content is mem0's ranked/capped `memory_search`.

## Decision

**1. Surface the relevance signal that already existed.** `memory_search` in `crates/mcp/src/task_server/tools/mem0.rs` now tracks the scores of the hits that survive dedup/cap and logs `top_score` and `avg_score` alongside the existing `hits` count in the `tracing::info!(target: "mem0", ...)` line. No change to the tool's return shape (`memories: Vec<String>`) — this is observability only, not a new agent-facing contract.

**2. A structured-diff regression test, in `mem0-vk/test/`** (not runtime code) — `context-drift.test.ts`:
   - Simulates a handoff: stores 2 "signal" facts scoped to a task (a distinctive marker token), then stores a pool of unrelated "noise" facts (simulating a repo's accumulated project memory), then searches with a task-scoped query.
   - Produces a structured diff: `retrieved` (id, score, content, whether each hit is signal or noise), `hits`/`missed` (which signal facts made it into the top-`limit`), `recall`, `noise_intrusions`.
   - Asserts a regression floor: recall must be 1 and no noise fact may outrank a signal fact for this scenario. A future change to embedding, ranking, dedup, or cap logic that quietly degrades recall now fails CI/local test runs instead of silently degrading production handoffs.
   - Required fixing the stub embedding first: `test/harness.ts` (new — factored out of `test.ts`, which now imports it) replaced the positional character-histogram `stubEmbedding` with a deterministic bag-of-words hash (lowercased words → hashed bucket, counted, L2-normalized). The old stub had no similarity structure at all — texts sharing words did not reliably score higher than unrelated texts — so it could not support any recall assertion. Verified: with the histogram stub, the drift test's signal facts scored *below* random noise (recall 0); with the bag-of-words stub, signal scored 0.674 vs. 0 for disjoint-vocabulary noise (recall 1). `test.ts`'s existing 36 checks still pass unchanged against the new stub — none of them depend on ranking precision, only on results existing.

## Consequences

- `mem0-vk`'s logs now carry a per-call relevance signal (`top_score`, `avg_score`), cheap to scrape into a dashboard or alert on later if desired — not done here.
- `npm run test:drift` (in `mem0-vk/`) is a repeatable regression guard for recall quality; `npm test` remains the fast wiring smoke test. Both share `test/harness.ts`.
- Trade-off: the bag-of-words stub embedding validates the mem0-vk scoring/ranking *mechanism* (sort, dedupe, cap), not the semantic quality of whatever real embedding backend is configured in production (sentence-transformers, OpenAI, etc.) — it cannot catch a production embedding model regressing.
- Trade-off: `SPEC.md`/`IMPLEMENTATION_PLAN.md` raw-text handoff still has no drift/loss measurement — by design there's nothing to measure there (the whole file is read, nothing ranked or dropped). If that changes (e.g. the file is summarized or truncated before handoff), this ADR's approach would need a counterpart there too.

## Addendum: real-embedding, extraction-quality, and debug-only monitoring

The trade-off above — the stub can't catch a real embedding regression — was addressed directly rather than left open:

**1. `mem0-vk/test/semantic-recall.test.ts`** exercises the REAL embedding backend (docker-compose's `embeddings` sidecar — sentence-transformers `all-MiniLM-L6-v2`, local CPU, no API key/cost), via `harness.ts`'s new `startApp({ realEmbedding: true })`: extraction is left unconfigured, so `extractStructure`'s fallback stores the raw input verbatim (no LLM call), keeping content fully test-controlled while embeddings are the real model. Two scenarios:
   - A sanity check (same signal/noise shape as `context-drift.test.ts`, real embedding).
   - An adversarial paraphrase check: the query shares **zero literal words** with the fact it must retrieve, and the noise pool includes lexical decoys that share surface vocabulary with the query but are semantically unrelated — a check a bag-of-words ranker could never pass by accident. Verified: real result was signal score 0.4717 vs. decoy scores 0.10–0.23, despite no shared words at all.

**2. `mem0-vk/test/extraction-quality.test.ts`** tests the OTHER thing the stub can't touch: whether the real extraction LLM's entity/relation output is any good. Unlike every other test file, it does not spawn an isolated process — it hits the *live* running container (`localhost:8000`) directly, scoped to a dedicated `user_id`, so it never needs to see or hold an API key (the live container already has one loaded). Runs a few known texts through real extraction (groq in dev), asserts lenient keyword-presence checks against the extracted entities/relations. **Discovered real, load-bearing non-determinism in the process**: the free-tier model (`qwen/qwen3.6-27b` via groq) sometimes returns a valid `facts` array but empty `entities`/`relations` — confirmed across repeated live runs (one run 3/3 cases produced a graph, another 1/3), almost always *silently* (only one instance was ever logged server-side as `[llm] ... no JSON object, failing over`; the rest were syntactically valid JSON with empty arrays). Because of this, the test asserts a **majority** threshold (`MIN_GRAPH_SUCCESS_RATIO = 0.5`), not "every case must produce a graph" — a single flaky call must not fail the suite, but the extraction path going systematically graph-empty still will. This is a genuine finding about production extraction reliability that the mechanism/ranking tests could never have surfaced.

**3. Debug-build-only relevance monitoring.** `crates/mcp/src/task_server/tools/mem0.rs::warn_if_weak_relevance` logs a `tracing::warn!` when a `memory_search` call's top score is below `WEAK_RELEVANCE_THRESHOLD` (0.3, an unvalidated starting point) or has hits with no score at all. Gated with `#[cfg(debug_assertions)]` on both the function and its call site — `debug_assertions` is `true` for `cargo build`/`check`/`test` (dev profile) and `false` for `cargo build --release` by default, and the workspace's `[profile.release]` doesn't override it — so this check, and its log output, compiles out of and never runs in a release binary entirely. It's a local-development signal layered on top of the `top_score`/`avg_score` info-level log (which does ship to production, per the main Decision above) — deliberately not a production alerting mechanism.

**4. Incidental bug fix: test cleanup was silently no-op-ing.** While verifying the above, discovered every test file's teardown (`test.ts`, `context-drift.test.ts`, and this ADR's original `semantic-recall.test.ts`) called `process.exit()` immediately after firing an unawaited `fetch(..., { method: "DELETE" })` — `process.exit()` tears the process down before that promise can resolve, so the Qdrant test collection was never actually deleted; only the `process.on('exit', cleanup)` safety net looked like it was doing cleanup, but a synchronous 'exit' handler can't complete async work either. Orphaned `test-*`/`test-drift-*` collections had been accumulating in Qdrant across every prior run. Fixed by making `cleanup` async and `await`-ing it at every call site before `process.exit()`; the `'exit'` listener now only does the synchronous part (kill the spawned child process) as a last-resort fallback. Verified: `docker`'s Qdrant collection list is back to just the real `mem0-vk` collection after a full run of all four suites.

**5. Root cause of the extraction non-determinism, fixed at the source.** Investigating item 2's finding further: the flakiness wasn't a config gap in the fallback chain (`llmCandidates()` already orders `[primary, ...rest]` correctly) — it was that `llmChat`'s failover only ever triggered on network error, HTTP 429, non-ok status, or a response with no parseable JSON object at all (`mem0-vk/src/index.ts`). A candidate that returned syntactically valid JSON like `{"facts": [...], "entities": [], "relations": []}` was accepted as a *successful* extraction — the code had no way to know the graph came back empty, so it never tried the next candidate. `llmChat` now takes an optional `isAcceptable(content: string): boolean` predicate; a candidate whose response fails it is treated exactly like the no-JSON-object case (logged, failed over). `extractStructure` passes `hasGraphContent` (same clean-and-parse logic it already used, factored out) whenever `graphEnabled()` is true — so an empty-graph response now costs one extra failover hop instead of being silently kept. Verified live: `docker logs` showed `[llm] groq returned JSON but failed the acceptability check (e.g. empty graph), failing over to next provider` firing during an `npm run test:extraction` run, and that run came back 3/3 cases with a non-empty graph (previously as low as 1/3).

**6. Local llama-server registered as a fallback, without ever touching cloud secrets.** Separately, the running container's `.env` had never set `MEM0_LLAMA_URL`/`MEM0_LLAMA_MODEL`, so `llama` was filtered out of `llmCandidates()` entirely (`if (!url || !model) continue;`) regardless of item 5's fix — there was no third candidate to fail over *to*. Wired up a local llama.cpp instance (`llama-server`, Qwen3.8-27B chat GGUF, keyless — `llama` needs no API key per `llmCandidates()`) as that third candidate via `POST /api/config` (the same runtime-config endpoint the Settings → Memory UI already uses — `packages/web-core/.../MemorySettingsSection.tsx` → `crates/server/src/routes/usage.rs`'s `put_mem0_config` → this same mem0-vk endpoint), persisted to the mounted `/data/config.json`, so no `.env`/secret was read, written, or seen by the agent doing this. Confirmed the value survives both a plain restart and a full image rebuild. Confirmed the Settings UI already renders and can edit this exact field with no code changes needed — `MemorySettingsSection.tsx`'s `PROVIDER_ORDER` already includes `llama`.

**7. `top_score`/`avg_score` made visible in Settings → Usage, not just logs.** Item 1's `tracing::info!(target: "mem0", ...)` log line turned out to be effectively unobservable in practice: `memory_search` runs inside `vibe_kanban_mcp` (`crates/mcp/src/bin/vibe_kanban_mcp.rs`), a stdio-transport MCP server the coding agent CLI spawns as its own child process — its stderr (where `init_process_logging`'s `EnvFilter::new("debug")` writes) is not captured or surfaced by vibe-kanban anywhere; whether it's visible at all depends entirely on how the spawning agent CLI handles its MCP child's stderr. So the drift signal this ADR set out to expose was, in effect, still invisible.

Closed the gap by giving it a real, always-on home in the Settings → Usage UI, next to the existing "mem0 extraction tokens" panel:
- **`crates/services/src/services/mem0_relevance.rs`** (new) — `Mem0RelevanceService`, an in-memory day-bucketed ledger (same pattern as `queued_message.rs`'s `QueuedMessageService`: a `DashMap`, no DB table, resets on server restart — an observability aid, not data worth persisting). `record(top_score: Option<f64>)` buckets a call into today's `calls`/`weak_calls`/running score sum by the same `WEAK_RELEVANCE_THRESHOLD = 0.3` used in `mem0.rs` (duplicated as a constant — the crates don't share a dependency edge that direction). `summary()` returns the last 30 days plus totals. 4 unit tests (`cargo test -p services mem0_relevance`) cover strong/weak bucketing, the `None`-counts-as-weak-but-not-in-the-average rule, the exactly-at-threshold boundary, and the 30-day cutoff.
- Wired into `Deployment`/`LocalDeployment` exactly like `queued_message_service()` (new trait method, new field, new constructor line).
- **`POST /api/usage/mem0-relevance`** (new, `crates/server/src/routes/usage.rs`) — the *only* channel `vibe_kanban_mcp` (a separate OS process, no shared memory with the main `server` binary) has to get this data into that server's `UsageSummary`. Takes `{ top_score: Option<f64> }`, calls `Mem0RelevanceService::record`, always returns success (an observability sink must never surface an error to whatever is reporting into it). `UsageSummary` gained a `mem0_relevance: Mem0RelevanceSummary` field, filled from `deployment.mem0_relevance_service().summary()`.
- **`memory_search` reports after every call** (`crates/mcp/src/task_server/tools/mem0.rs`) — `report_mem0_relevance(url, client, top_score)`, spawned via `tokio::spawn` rather than awaited inline: this must add zero latency to the tool call it's reporting on, and a failure (VK API down, network hiccup) must never surface to the agent, matching the file's existing "mem0 must never block an agent" ethos. `WEAK_RELEVANCE_THRESHOLD` in this file stayed `#[cfg(debug_assertions)]`-gated (it's genuinely only used by the debug-only console warning now — the threshold comparison for the always-on report happens server-side, in `mem0_relevance.rs`, on the raw `top_score` this function sends).
- **Settings → Usage UI** (`packages/web-core/.../UsageSettingsSection.tsx`) — new "mem0 recall relevance" panel, same visual language as the tokens panel: total calls (+ weak-call count in `text-warning` when non-zero), per-day bar chart where bar width is `avg_top_score` (0–1 → 0–100%) and color is red/amber/green split at 0.3/0.6. New `Mem0RelevanceDay`/`Mem0RelevanceSummary` TS interfaces hand-written to mirror the Rust structs, following this file's existing pattern (this feature area isn't wired through the ts-rs `generate-types` pipeline — `UsageSummary`/`Mem0TokenUsage` aren't in `shared/types.ts` either).
- Verified end-to-end via `curl POST /api/usage/mem0-relevance` against the live dev server (auto-rebuilt by `cargo watch`) with `{0.55}`, `{0.15}`, `{null}`: `GET /api/usage/summary` correctly returned `calls: 3, weak_calls: 2, avg_top_score: 0.35` (mean of the two *scored* calls only, `null` counted as weak but excluded from the average) — confirming the full MCP-report → service → API → (by inspection, since no browser-automation tool was available to screenshot) UI-consuming-shape chain. Not visually screenshotted; `tsc`/`eslint` pass and the JSX was code-reviewed against the existing tokens panel it mirrors.

## Addendum: real graph navigation, an end-to-end quality experiment, and fact/graph provenance

Prompted by a discussion of whether mem0's graph (entities/relations, NetworkX) is validated infrastructure or unvalidated complexity (see akitaonrails' "harness/loop/graph engineering são bullshit" critique — its core claim is that most of this category is unmeasured complexity sold as methodology). The honest answer going in: nothing in this repo had ever tested whether the graph beats flat vector recall for planning. This addendum closes that gap directly, with a real measurement, not a bigger assumption.

**1. `/graph/neighbors` (the only existing "graph query") was not navigation.** Read closely (`mem0-vk/embeddings/app.py`): it substring-matches the query text against node names/descriptions, then expands exactly **one** hop of `g.successors()` only — the graph is a directed `NetworkX.DiGraph`, so this misses everything pointing *at* the matched nodes entirely, and there is no depth parameter. There was no way to ask "what's connected to X within N hops, in either direction."

**2. Built real traversal: `/graph/traverse`** (`mem0-vk/embeddings/app.py`) — proper BFS from substring-matched start node(s), configurable `hops` (capped at 3) and `direction` (`out`/`in`/`both`, meaningful because the graph is directed), capped at 40 returned nodes (mirrors `DEFAULT_SEARCH_LIMIT`'s "must not flood context" rationale from ADR-028). Wired through: `mem0-vk/src/index.ts`'s `graphTraverse()` + `POST /api/graph/traverse`, then a new MCP tool **`memory_graph_traverse`** (`crates/mcp/src/task_server/tools/mem0.rs`) — same graceful-degradation contract as `memory_search`/`memory_save` (mem0/graph absence → empty result, never a failed tool call). Added to `global_mode_router`'s exact-set registration test (`crates/mcp/src/task_server/tools/mod.rs` — "adding a tool is a deliberate act"). Verified through the **actual agent-facing path**: a raw stdio JSON-RPC driver script talking to the real `vibe-kanban-mcp` binary (not a curl against mem0-vk directly) confirmed `tools/list` includes it and `tools/call` returns real traversal data, correctly formatted.

**3. The validation experiment, run against this repo's own real accumulated project memory** (not synthetic data — `vibe-kanban-alternative.graphml`, built from past real `memory_save` calls across earlier sessions): compared `memory_search` (vector, query *"how does graph extraction work, what LLM provider is used"*) against `memory_graph_traverse` (2 hops, both directions, from the `Groq` node the vector search surfaced).
   - **Vector top-5**: five near-duplicate facts, all confirming "Groq/qwen3 does extraction, saved as GraphML" — no architectural information.
   - **Graph traversal**: 16 nodes/16 edges. Genuinely surfaced information vector search's top-5 completely missed — `mem0-vk -[provides]-> REST API/MCP`, `-[runs_on]-> Docker` — real architecture, not paraphrases of the same fact.
   - **But**: a meaningful fraction of what came back was garbage — `mem0 -[uses]-> LazyLock`, `-[uses]-> Regex`, `-[logs_warning_on]-> "failure to save VK-MEMORY fact"` are **direct references to the `VK-MEMORY` marker mechanism ADR-028 removed**. The graph doesn't know that code is gone. `vibe-kanban-alternative -[has]-> Archive` is a generic, low-information project-level edge that adds noise, not architecture.
   - **Verdict**: the graph earns its complexity — it surfaces real structural information flat vector recall structurally cannot (associative similarity vs. topology) — but is unsafe to hand an agent as-is: it mixes live signal with dead references at a rate that would actively mislead planning, not just add noise. This is measured evidence, not a hunch: staleness isn't a theoretical risk here, it's what the very first traversal against real data returned.

**4. Fact + graph provenance (commit SHA), to make staleness detectable** — the direct, concrete fix the experiment's own findings called for. Every fact (Qdrant point) and every graph node/edge now optionally carries `commit_sha`: the calling workspace's HEAD commit at save time, best-effort and additive (nothing breaks without it — old data has none).
   - `crates/mcp/src/task_server/tools/mem0.rs`'s `memory_save` resolves it via a new best-effort helper, `resolve_commit_sha`: matches `user_id` (repo slug) against `self.context.workspace_repos`, then calls the **already-existing** `GET /api/workspaces/{id}/git/status` (`crates/server/src/routes/workspaces/git.rs` — no new server route needed; its `RepoBranchStatus.head_oid` was already exactly what was needed) and reads that repo's `head_oid`. Any failure — no context, no matching repo, VK API down, no commits yet — degrades to `None`, never blocks the save. Verified the real response shape (`repo_id`, `head_oid` fields, `{success, data, ...}` envelope) against a live workspace in this repo's own DB before trusting the deserialize types.
   - `mem0-vk/src/index.ts`: `memoryStore`/`pushToGraph` accept and forward `commit_sha`; `POST /api/memories` accepts it in the request body; stored in the Qdrant point payload alongside `content`.
   - `mem0-vk/embeddings/app.py`: `UpsertRequest.commit_sha`; `GraphStore.upsert` stamps it onto every node/edge touched by that call, **last-write-wins** (a node reinforced across many calls at different commits keeps only the most recent stamp — a deliberate simplification, not full history). `/graph/traverse`'s node/edge output now includes `commit_sha`.
   - Verified end-to-end against the live containers: stored a fact with `commit_sha: "abc1234"`, confirmed it on both the Qdrant payload (`GET /api/memories/:user_id`) and the graph node (`POST /api/graph/traverse`).
   - **What this ADR does NOT yet do**: actually *use* `commit_sha` to prune or flag anything. This addendum is the capture side only — a deliberate, minimum-testable-slice stop, matching this ADR's own methodology (measure before building the next layer). The next piece, not yet built: a staleness check comparing a fact's `commit_sha` against current HEAD / whether files touched since then invalidate it — discussed as two different-cost approaches (naive: grep the node name against the current repo, no provenance needed, imprecise; provenance-based: check whether the specific commit's relevant files/symbols still exist, precise, needs exactly the data this addendum now captures). The `VK-MEMORY` false-positive risk for naive string matching (the name could coincidentally exist elsewhere in the repo even after the original reference is gone) is why provenance was chosen over the naive approach.
   - **Also not yet done**: the identical staleness problem exists on the vector-fact side for the exact same reason (a fact's truth can silently rot with no visual signal the way a graph node's obsolete edges are at least inspectable) — `commit_sha` is now captured there too, for the same future pruning mechanism to use once built.

## Addendum 2: the staleness check itself — `memory_check_staleness`

Built directly on the provenance captured above, closing the loop the previous addendum deliberately left open.

**Why "is `commit_sha` an ancestor of HEAD" doesn't work.** The obvious cheap check — `git merge-base --is-ancestor <commit_sha> HEAD` — was considered and rejected. In ordinary linear development, a fact's save commit stays an ancestor of HEAD *forever* even after everything it describes is deleted three commits later; ancestry only breaks on history rewrites (force-push, rebase-away), which is rare. This check would not have caught the `VK-MEMORY`/`LazyLock`/`Regex` case that motivated this whole line of work — the commit that added the mem0.rs marker-parsing code is still a perfectly good ancestor of current HEAD; what makes those facts stale is that a *later* commit deleted the file, which ancestry-checking cannot see.

**What actually catches it: diffing since the fact's commit and looking for the entity in REMOVED lines.** `git diff <commit_sha>..HEAD` shows exactly what changed since the fact was true, including deletions — `-`-prefixed lines are content that existed then and doesn't now. Matching the entity name against just those lines is precise in a way a plain "grep the current repo" (the naive approach from Addendum 1) is not: a bare current-state grep can't distinguish "never existed here" from "used to be referenced right here and was deleted," and can false-negative on a name that happens to still exist somewhere unrelated in a large repo.

**Implementation:**
- **`GET /api/workspaces/{id}/git/diff-since?repo_id=&commit_sha=`** (new, `crates/server/src/routes/workspaces/git.rs`) — generic git primitive, not mem0-specific plumbing (any future consumer could use "what got removed since commit X in this repo"). Validates `commit_sha` resolves in the worktree first (`git cat-file -e <sha>^{commit}`) — an unresolvable commit (rewritten history) returns `commit_found: false` rather than a crash or a misleadingly-empty diff. Returns the concatenated removed-content lines (`-` lines, `---` file-header lines excluded) via the CLI (`GitCli::git`, the same wrapper `GitService` uses elsewhere in this crate — chosen per that module's own documented reasoning: CLI over libgit2 for diff correctness), capped at 200KB with a `truncated` flag. **Verified against this repo's own real history**: `commit_sha` = this session's earlier "measure context drift" commit, diffed to current HEAD, correctly surfaced the `handleSendLive`/`headedLive` code this session itself wrote and then removed a few commits later (the headed-send routing fix) — an unplanned but clean real-world confirmation the mechanism works, using code changes made *during this same session* as the test fixture.
- **`memory_check_staleness`** MCP tool (`crates/mcp/src/task_server/tools/mem0.rs`) — takes `{user_id, entity}` only; the agent doesn't need to hunt down a commit_sha itself. Internally: (1) a 1-hop `memory_graph_traverse` lookup to read the entity's own stored `commit_sha` (the start node is always included in a traversal's own results, so hops=1 is the cheapest valid call for "just this node's data"); (2) `resolve_workspace_repo`, a small refactor pulled out of `resolve_commit_sha` (Addendum 1) since both now need the same `user_id` → `(workspace_id, repo_id)` lookup from `self.context`; (3) call `diff-since` with that commit; (4) case-insensitive substring match of `entity` against the removed-lines text, capped at `MAX_STALENESS_EVIDENCE_LINES = 5` matches. Registered in `global_mode_router` and the "adding a tool is a deliberate act" exact-set test.
  - `checked: false` is the honest-uncertainty return for every failure mode (no provenance recorded for this entity — it predates commit_sha tracking — graph/mem0 down, VK API unreachable, or the resolved commit no longer exists in this worktree). The tool never claims a fact is fresh; it only reports whether removal evidence was or wasn't found for entities it *could* check.
  - `memory_graph_traverse`'s own node/relation output now also surfaces `commit_sha` (`[commit 7a7148f]`, git's own 7-char convention) — captured in Addendum 1's Python/graph work but never wired into the Rust deserialize types or the agent-facing formatted text until now. Without this, an agent had no way to *see* which nodes might be worth staleness-checking in the first place.

**Verification.** `/graph/traverse` and `/git/diff-since` were each independently confirmed correct against real production data (this repo's own accumulated project memory graph; this repo's own real commit history) via direct HTTP calls. `memory_graph_traverse` was already proven end-to-end through the actual agent-facing stdio path in Addendum 1. `memory_check_staleness` compiles clean, passes the full existing `mcp`/`server` test suites (including the updated tool-registration exact-set test), and clippy/fmt are clean — but its own live stdio round-trip could not be completed: reproducing it requires the MCP process's context-resolution probe (`GET /api/containers/attempt-context`, pre-existing code, untouched by this work) to succeed against a manually-scripted harness's `cwd`, and that probe returned the SPA HTML fallback rather than JSON for *every* `/api/containers/*` route tried (including `/containers/info`, documented as required by the VSCode extension) against the currently-running dev server — a pre-existing environment/routing characteristic unrelated to anything built in this ADR, not chased further given the strength of the piece-by-piece verification already in hand.

## Addendum 3: `mem0-vk/Dockerfile` never actually built the code it shipped

Discovered while confirming this session's `mem0-vk`/`embeddings` source changes would survive a fresh `docker compose up -d --build` rather than only working because a local `dist/` happened to already be built. They would not have: `mem0-vk/Dockerfile` did `COPY dist/ ./dist/` and never ran `tsc` — it copied a pre-built directory that `mem0-vk/.gitignore` explicitly excludes from the repo. Every rebuild this session succeeded only because `npm run build` had just been run locally by hand immediately before each `docker compose up -d --build`; the two-step habit masked that the single documented command in `mem0-vk/README.md`'s Quick Start (`cd mem0-vk && docker compose up -d --build`, no build step first) would fail on a truly fresh clone at the `COPY dist/` step — `dist/` wouldn't exist.

Fixed with a standard two-stage Dockerfile: a `build` stage installs full deps and runs `npm run build` (`tsc`) from `src/`, a second runtime stage installs only prod deps and `COPY --from=build`s the compiled `dist/`. Verified for real, not just read: deleted local `dist/` and `node_modules` entirely (matching a fresh clone's state) and ran `docker compose build mem0-vk --no-cache`, which built and compiled successfully with zero manual steps; redeployed the live container and confirmed the runtime-config volume (Addendum 1's `llama` fallback provider) and `/graph/traverse` both survived the recreation.

## Addendum 4: `self.context` had been `None` for every MCP session for 19 days — found while investigating why `memory_check_staleness` couldn't be verified live

Addendum 2 closed with an honest gap: `memory_check_staleness`'s live stdio round-trip couldn't be completed because the MCP process's context-resolution probe returned the SPA HTML fallback for every `/api/containers/*` route. Investigating that gap (rather than accepting it) found the real cause, and it is much bigger than this ADR's own scope.

**Root cause**: `e41e2c16` ("refactor: remove cloud/remote stack (Phase 1)", 2026-08-02, 208 commits before this one) deleted `pub mod containers;` and its `.merge(containers::router(&deployment))` from `crates/server/src/routes/mod.rs` — grouped in the same diff hunk as genuinely cloud-only modules (`oauth`, `host_relay`, `relay_auth`, `remote`, `webrtc`). `containers.rs` (`GET /api/containers/attempt-context` → `get_context`, `GET /api/containers/info` → the VSCode extension's endpoint) was always purely local — a DB lookup, no cloud dependency — caught as collateral damage, not an intentional removal. This is the exact same failure class the pre-existing `global_mode_exposes_the_full_card_surface` test comment already documents happening to the issue/project MCP tools in that same commit ("nothing failed... every board-driving agent silently lost its entire card surface") — except this instance was never caught or restored.

**Blast radius**: with the route gone, `crates/mcp/src/task_server/mod.rs`'s `fetch_context_at_startup` silently got no context on every MCP session start (its own code already treats a failed/empty probe as "no context" in global mode, by design, for exactly this "not a worktree" case — so it never surfaced as a crash or an error, just silent absence). Concretely, for 19 days: `get_context` was never registered as an available tool; `self.context` was `None` everywhere, so `orchestrator_session_id()`/`scoped_workspace_id()` always returned `None`; every tool whose docs promise an implicit-context fallback silently required an explicit parameter instead — including this session's own `resolve_commit_sha`/`resolve_workspace_repo` (Addenda 1-2) AND, discovered while confirming this fix's scope, the concurrently-developed `report_pipeline_stage` tool (`crates/mcp/src/task_server/tools/workspaces.rs`, added in a parallel session's `08139681`), whose own tool description promises `workspace_id` is "optional if running inside that workspace context" via the identical `resolve_workspace_id` → `scoped_workspace_id()` fallback path.

**Fix**: restored the two deleted lines — `pub mod containers;` and `.merge(containers::router(&deployment))` — in `crates/server/src/routes/mod.rs`. `containers.rs` itself needed no changes; every type and method it depends on (`ContainerQuery`, `Workspace::resolve_container_ref_by_prefix`, `Workspace::load_context`, `WorkspaceContext`) was still current and unchanged 208 commits later — it had simply never been reconnected.

**Verification, all against the live dev server with real data — not simulated**:
- `GET /api/containers/attempt-context?ref=<real workspace container_ref>` now returns the real `WorkspaceContext` (workspace, repos, `orchestrator_session_id`) instead of SPA HTML. (The query param is `ref`, not `container_ref` — `ContainerQuery` has `#[serde(rename = "ref")]`; the MCP client already sent it correctly via typed serialization, only a manual curl test needed the correction.)
- `GET /api/containers/info` (the VSCode-extension-required endpoint) confirmed working the same way.
- Full stdio JSON-RPC round-trip against the real `vibe-kanban-mcp` binary, cwd'd into a real workspace directory: `get_context` is now a listed tool and returns real, correct data.
- **`memory_check_staleness`'s full positive path, finally provable**: injected a test fact (`commit_sha` = an earlier commit in this session where `handleSendLive` genuinely existed in `SessionChatBoxContainer.tsx`), then called `memory_check_staleness("handleSendLive")` through the real MCP path. Result: `checked: true, commit_found: true, likely_stale: true`, with `evidence` containing the exact two removed lines from the real later commit that deleted it. The entire chain — context resolution → graph lookup → commit validation → diff → removed-line matching — confirmed correct end to end, through the real agent-facing surface, with real data. Test artifacts (the injected fact and graph nodes) were deleted afterward.
- `cargo test -p server` (77 passed), `cargo test -p mcp --lib` (45 passed), `cargo check --workspace`, `cargo clippy`, `cargo fmt --check` — all clean.

## Addendum 5: closing the loop — cleaning the actual mess found, and getting agents to use the tools at all

Everything built through Addendum 4 was infrastructure an agent *could* call. Nothing yet told it to, and the specific stale data this whole investigation was triggered by (Addendum 3) was still sitting in production, uncleaned.

**Cleanup of the real `vibe-kanban-alternative` project memory** (not synthetic — the repo's own accumulated mem0 data): removed the graph nodes `VK-MEMORY`, `LazyLock`, `Regex`, `failure to save VK-MEMORY fact` (all specifically about the marker-parsing mechanism ADR-028 removed — confirmed via that ADR's own text, not via `memory_check_staleness`, since none of these nodes carry `commit_sha` — they predate provenance tracking, so the tool can only honestly say "unknown" for them; this is exactly the documented limit of what provenance-based checking can do). Also found and removed the `mem0 -[watches]-> execution logs` edge (the same removed `spawn_memory_tracker` mechanism, missed on the first pass — caught by checking what else pointed at the same node before deleting it, and confirmed nothing else in the graph depended on it). On the vector side: 5 facts making the same now-false claims, plus one unrelated, separately-discovered corrupted entry (a raw JSON tool-output dump saved as if it were a fact — a different bug, not staleness, from some earlier session). Two large multi-topic session-summary facts still mention `VK-MEMORY` in passing among many still-valid details — deliberately left alone rather than deleted, since removing the whole fact to fix one outdated clause would throw away everything else true in it; this is a granularity problem `memory_check_staleness` (or naive deletion) can't solve, only re-extraction/editing could.

**Pipeline "memory" stage prompts** (`assets/pipelines/*.toml`, 9 files: 8 sharing identical prompt text plus `swarm-multi-agent.toml`'s own distinct cross-stage-handoff version) now instruct the agent to use both new tools where the existing prompt already asked it to do the equivalent job by unaided judgment: the old text said "ignore irrelevant or stale ones" with no way to actually check; it now says to call `memory_graph_traverse` when a hit names an entity worth understanding structurally, and `memory_check_staleness` when a hit looks old or inconsistent with the code actually being seen, before trusting it. `swarm-multi-agent.toml`'s version additionally names the specific reason this matters most there: work is handed across stages and sometimes across different agent CLIs, so a fact one stage saved can go stale before a later stage reads it. Verified via the real Rust loader, not just read: `cargo test -p services pipelines` (24 tests, including `seeds_defaults_into_empty_dir`, which parses all 9 bundled files via `toml::from_str`) passes unchanged.
