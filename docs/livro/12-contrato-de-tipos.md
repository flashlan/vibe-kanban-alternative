# Capítulo 4 — O contrato de tipos: ts-rs na prática

> **Princípio:** se duas linguagens precisam concordar sobre um formato, gere o formato a partir de uma fonte única. Convenção diverge; contrato gerado não.

## O problema

Num projeto Node + Rust, os dois lados concordam o tempo todo sobre a mesma coisa: o que é um `Project`, um `Workspace`, uma `Issue`, um `ExecutionProcess`. Se cada lado declara o tipo à mão, basta um campo mudar num lado para o outro quebrar em runtime — e um agente de IA, que lê um lado e escreve no outro, é o primeiro a introduzir a divergência.

O antídoto deste repositório é curar a fronteira como contrato: um lado é a fonte da verdade, o outro é gerado.

## Como funciona aqui

A fonte da verdade são os structs Rust anotados com `#[derive(TS)]` do crate `ts-rs`. O binário `crates/server/src/bin/generate_types.rs` coleta `TS::decl()` de dezenas de tipos — `Repo`, `Project`, `Workspace`, `Session`, `ExecutionProcess`, `Merge`, `Scratch` etc. — e escreve `shared/types.ts`.

O arquivo gerado abre com o aviso que todo agente precisa respeitar (`crates/server/src/bin/generate_types.rs:10`):

```ts
// This file was generated by `crates/core/src/bin/generate_types.rs`.
// Do not edit this file manually.
// If you are an AI, and you absolutely have to edit this file, please
// confirm with the user first.
```

O `AGENTS.md` raiz reforça: "Do not manually edit `shared/types.ts`, instead edit `crates/server/src/bin/generate_types.rs`." O CI reforça com `pnpm run generate-types:check`, que falha se o arquivo gerado estiver desatualizado.

O comando canônico:

```bash
pnpm run generate-types          # regenera shared/types.ts
pnpm run generate-types:check    # só verifica, usado no CI
```

Na prática: você adiciona um campo num struct Rust em `crates/db/src/models/` ou `crates/api-types/`, roda `generate-types`, e o TypeScript passa a conhecer o campo — sem redeclaração. O `cargo check` e o `tsc` quebram juntos se a forma divergir, o que é exatamente o que você quer: erro cedo, na compilação, não em runtime.

## A exceção consciente: um contrato congelado

Nem todo contrato gerado deve continuar gerado. Quando o fork removeu os crates `remote` e `relay-*`, o generator de `shared/remote-types.ts` foi embora junto. Mas `shared/remote-types.ts` **permaneceu** — porque ele é o contrato do data layer do kanban local (`providers/remote/*`, `integrations/electric/*`, `lib/electric/*`) consumido pelo frontend em modo fallback-REST. O `AGENTS.md` chama isso pelo nome: "treat it as a frozen, hand-maintained contract since its generator has been removed".

Lição transferível: contrato gerado é o padrão; contrato congelado é a exceção documentada, com motivo. Sem o registro, alguém apagaria o arquivo achando que é lixo.

## Schemas de tools de agentes

O mesmo espírito aparece em `shared/schemas/`: os schemas das tools que os agentes usam são compartilhados entre Rust e TypeScript. Mudar a forma de uma tool sem atualizar o schema quebra os dois lados — por isso o schema vive no meio, versionado.

## O que isso ensina sobre spec-driven

"Spec-Driven Architecture" não é só escrever um documento antes de codar. É escolher onde a spec vive. Aqui, a spec da fronteira vive nos structs Rust com `#[derive(TS)]` — o código **é** a spec, e o gerador garante que ninguém desobedeça em silêncio. A spec de pipeline vive em `assets/pipelines/*.toml`; a spec de como um card reporta progresso vive nos marcadores `VK-PIPELINE-STAGE` e `VK-REVIEW-REQUEST` (cap. 6). Em cada caso, a ideia é a mesma: uma fonte, uma geração, zero divergência por esquecimento.

## Checklist do capítulo

- [ ] Cada tipo que atravessa a fronteira tem uma única fonte (Rust com `#[derive(TS)]`).
- [ ] Existe um comando único que regenera o lado TypeScript (`generate-types`).
- [ ] O arquivo gerado tem banner "Do not edit manually" e o CI verifica desatualização.
- [ ] Exceções (contratos congelados) estão documentadas com o motivo de existirem.
- [ ] Schemas de tools de agentes são compartilhados, não duplicados.
